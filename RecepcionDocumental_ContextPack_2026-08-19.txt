5. CAMBIO DE REQUISITO DE NEGOCIO
============================================================

La empresa indicó que POR AHORA sólo interesan FACTURAS.

No interesa conservar:
- remitos
- órdenes de compra
- presupuestos
- notas de pedido
- archivos irrelevantes
- otros adjuntos que no sean factura

Por eso se definió H1D — Selector de Facturas.

Regla general:
Gmail attachment -> analizar -> FACTURA / REVISAR / DESCARTAR

FACTURA:
- conservar físicamente
- guardar en SQL

REVISAR:
- conservar físicamente en carpeta Revisar
- guardar en SQL

DESCARTAR:
- no conservar físicamente
- no guardar en SQL

Decisión explícita:
NO llenar SQL con adjuntos descartados. Sólo persistir facturas y dudosos.

Consecuencia aceptada:
si alguna vez vence historyId y se hace fallback, un descartado podría volver a analizarse.

7. ZIP — DECISIÓN FUNCIONAL
============================================================

ZIP es un CONTENEDOR.

Flujo:
attachment ZIP
  -> Trabajo\<GUID>
  -> descomprimir
  -> recorrer todos los documentos
  -> clasificar cada documento individualmente
  -> conservar sólo FACTURA / REVISAR
  -> descartar el resto
  -> eliminar completamente el workspace

Un ZIP puede producir 0, 1 o varias facturas y/o documentos a Revisar.

El ZIP original normalmente NO se conserva después de procesarse bien.

Si el ZIP está corrupto, no puede abrirse, supera límites o es inseguro:
=> REVISAR / ZIP_NO_ANALIZABLE

ZIP anidado:
- soportado con profundidad controlada
- ejemplo: Proveedor.zip!/Documentos.zip!/Factura.pdf

No usar rutas internas del ZIP directamente como ruta física.

Decisión permanente:

- usar ICSharpCode.SharpZipLib para ZIP
- NO introducir PdfPig
- NO introducir iText
- NO introducir PDFsharp
- NO usar System.IO.Compression para esta función
salvo cambio expreso de criterio.

Código real de empresa inspeccionado:
- SharpZipLib: FastZip.ExtractZip(...) existe en código legado.
- Para RecepcionDocumental Codex usa ZipInputStream entrada por entrada para aplicar controles de seguridad.
- Mdoc: PdfReader, NumberOfPages, GetPageContent(...), objetos PDF/imágenes embebidas.

Advertencia:
GetPageContent no garantiza texto limpio para PDFs externos de proveedores.
Por eso una lectura parcial/codificada NO debe ser motivo para DESCARTAR una posible factura.

10. REGLAS H1D1A
============================================================

Señal explícita de factura:
- FACTURA A
- FACTURA B
- FACTURA C
- FACTURA M
- FACTURA E
- FACTURA DE CREDITO ELECTRONICA

Señales fiscales:
- CUIT
- CAE
- CAEA
- PUNTO DE VENTA / PTO VTA
- COMP NRO / COMPROBANTE / NRO COMPROBANTE
- IMPORTE TOTAL / TOTAL
- IVA
- FECHA DE EMISION

Señales claras de otros documentos:
- REMITO
- NOTA DE CREDITO
- NOTA DE DEBITO
- ORDEN DE COMPRA
- PRESUPUESTO
- RECIBO
- NOTA DE PEDIDO

Reglas conservadoras:
A) FACTURA explícita + >=3 señales fiscales => FACTURA
B) FACTURA explícita + señales insuficientes => REVISAR
C) >=3 señales fiscales fuertes sin factura explícita => REVISAR
D) señal fuerte de otro documento y sin evidencia fuerte de factura => DESCARTAR
E) PDF con texto pero no concluyente => REVISAR / PDF_TEXTO_NO_CONCLUYENTE
F) PDF sin texto útil => REVISAR / PDF_SIN_TEXTO

La palabra FACTURA sola NO alcanza.
Si hay evidencia fuerte de factura y también aparece REMITO, gana FACTURA.
Un PDF multipágina que contenga una factura se conserva completo.

13. CORRECCIÓN PREVALIDACIÓN IMPORTANTE
============================================================

Primera implementación peligrosa:
Mdoc recupera >=30 caracteres + no encuentra FACTURA => DESCARTAR

Se corrigió porque GetPageContent puede producir contenido parcial/codificado.

Nueva regla:
PDF con texto aparentemente útil pero NO concluyente => REVISAR
NO DESCARTAR.

Sólo descartar automáticamente cuando hay evidencia positiva clara de otro tipo documental.

Principio actual:
preferir falsos REVISAR antes que falsos DESCARTAR.
